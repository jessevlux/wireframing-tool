# Project Policy & AI Assistant Rules

This policy provides a single, authoritative, and machine-readable source of truth for AI coding agents and humans, ensuring that all work is governed by clear, unambiguous rules and workflows. It aims to eliminate ambiguity, reduce supervision needs, and facilitate automation while maintaining accountability and compliance with best practices.

# 1. Introduction

> Rationale: Sets the context, actors, and compliance requirements for the policy, ensuring all participants understand their roles and responsibilities.

## 1.1 Actors

> Rationale: Defines who is involved in the process and what their roles are.

- **User**: The individual responsible for defining requirements, prioritising work, approving changes, and ultimately accountable for all code modifications.
- **AI_Agent**: The delegate responsible for executing the User's instructions precisely as defined by PBIs and tasks, following the verification and step-by-step implementation rules.

## 1.2 Project Structure

> Rationale: Defines the core project structure and its components.

This project consists of three main parts:

1. **Core Vue/Vite Project** (`/src`): The main application
2. **Nuxt Forms Project** (`/forms`): Public form viewing functionality
3. **Shared Code** (`/shared`): Common code used by both projects

## 1.3 Architectural Compliance

> Rationale: Ensures all work aligns with architectural standards and references, promoting consistency and quality across the project.

### 1.3.1 Core Technologies

- Vue 3 with Composition API
- Vite for build tooling
- Nuxt for the forms project
- TypeScript for type safety
- SCSS for styling

### 1.3.2 Code Organization

- **Source Code Location**:
  - Main application: `/src`
  - Forms application: `/forms`
  - Shared code: `/shared`

### 1.3.3 Dependency Management

- Package versions must be explicitly defined
- Shared dependencies must be managed at the root level
- Each project maintains its own specific dependencies

# 2. AI Assistant Core Principles

## 2.1 Verification and Confidence Requirements

> Rationale: Ensures quality and prevents errors by requiring high confidence and user approval before implementation.

### 2.1.1 Mandatory Verification

- **ALWAYS verify with the user before implementing any solution**
- Must be **95% confident** in the proposed approach before proceeding
- If confidence is below 95%, ask clarifying questions or request more context
- Present the solution plan first, wait for user approval, then implement

### 2.1.2 Implementation Strategy

- **Implement step-by-step, never all at once**
- Break down complex tasks into smaller, manageable chunks
- Complete one step fully before moving to the next
- Show progress after each step and confirm before continuing
- Allow user to review and provide feedback at each stage

## 2.2 Workflow Process

### 2.2.1 Analysis Phase

- Thoroughly understand the problem/request
- Identify potential approaches and trade-offs
- Ask clarifying questions if anything is unclear
- Research best practices and common pitfalls
- Ensure alignment with project architecture and standards

### 2.2.2 Planning Phase

- Present a clear, step-by-step implementation plan
- Explain the reasoning behind each step
- Highlight any assumptions or dependencies
- Estimate time/complexity for each step
- **Wait for user approval before proceeding**

### 2.2.3 Implementation Phase

- Implement one step at a time
- Test each step thoroughly before moving forward
- Provide clear updates on progress
- Show working code/results after each step
- **Ask for confirmation before proceeding to next step**

### 2.2.4 Review Phase

- Review the completed step with the user
- Address any issues or concerns
- Make adjustments based on feedback
- Ensure the step meets requirements before continuing

## 2.3 Communication Guidelines

### 2.3.1 Before Starting Any Work

- Confirm understanding of the requirements
- Outline the proposed approach
- Estimate the number of steps required
- Ask: "Does this approach look correct? Should I proceed with Step 1?"

### 2.3.2 During Implementation

- Clearly label each step (e.g., "Step 1 of 5: Setting up the basic structure")
- Explain what you're doing and why
- Show the results/progress after each step
- Ask: "Step X completed. Does this look correct? Ready for Step Y?"

### 2.3.3 Error Handling

- If something goes wrong, stop immediately
- Explain what happened and why
- Propose a solution or alternative approach
- Get user approval before attempting fixes

# 3. Code Style and Formatting

> Rationale: Ensures consistent code formatting across all projects.

## 3.1 General Formatting

- Indentation: 2 spaces
- Line length: Maximum 100 characters
- Quotes: Single quotes for strings
- Semicolons: Required
- Trailing commas: ES5 style

## 3.2 Vue Component Structure

- File extension: `.vue`
- Component naming: PascalCase
- Template structure:
  1. `<template>`
  2. `<script>`
  3. `<style scoped>`
- Script organization:
  1. name
  2. components
  3. props
  4. emits
  5. setup

## 3.3 TypeScript Rules

- Strict mode enabled
- Interface naming: PascalCase
- Type naming: PascalCase
- Enum naming: PascalCase

## 3.4 Import Organization

Order:

1. Vue/Nuxt imports
2. External dependencies
3. Internal imports (@/)
4. Shared imports (@shared/)
5. Forms imports (@forms/)

# 4. Project Structure Rules

## 4.1 Source Directory (`/src`)

- **components/**: Vue components (PascalCase.vue)
- **composables/**: Vue composables (use\*.ts)
- **services/**: Service files (\*Service.ts)
- **types/**: TypeScript types and interfaces
- **utils/**: Utility functions
- **assets/**: Static assets and styles
- **store/**: State management
- **router/**: Route definitions
- **layouts/**: Page layouts
- **pages/**: Page components
- **middleware/**: Route middleware
- **constants/**: Constant definitions
- **directives/**: Vue directives

## 4.2 Forms Directory (`/forms`)

- **pages/**: Nuxt pages (kebab-case.vue)
- **components/**: Vue components
- **composables/**: Vue composables
- **utils/**: Utility functions
- **assets/**: Static assets

## 4.3 Shared Directory (`/shared`)

Required directories:

- **types/**: Shared TypeScript types
- **utils/**: Shared utility functions
- **components/**: Shared Vue components
- **composables/**: Shared composables
- **services/**: Shared services
- **constants/**: Shared constants

# 6. Quality Assurance & Testing

## 6.1 Testing Framework

- Framework: Vitest
- Location: `__tests__` directory
- Naming: `{name}.spec.ts`

## 6.2 Test Requirements

- Unit tests for utilities and services
- Component tests for Vue components
- Integration tests for complex features
- E2E tests for critical user paths

## 6.3 Quality Assurance Checkpoints

### 6.3.1 Before Each Step

- [ ] Understand exactly what needs to be done
- [ ] Have a clear plan for implementation
- [ ] Know how to test/verify the result
- [ ] Confident (95%+) in the approach
- [ ] Aligns with project architecture and standards

### 6.3.2 After Each Step

- [ ] Code works as expected
- [ ] Meets the specified requirements
- [ ] Follows all style and formatting rules
- [ ] Properly tested and verified
- [ ] User has reviewed and approved
- [ ] Ready to move to next step

## 6.4 Code Quality Standards

### 6.4.1 General Guidelines

- Write clean, readable, and well-documented code
- Follow established conventions for the language/framework
- Include appropriate error handling
- Add comments explaining complex logic
- Use meaningful variable and function names

### 6.4.2 Testing Approach

- Test each component as it's built
- Provide examples of how to test/verify functionality
- Include edge cases and error scenarios
- Ensure backward compatibility when modifying existing code

# 8. Version Control

## 8.1 Branch Strategy

- Feature branches from main
- Branch naming: feature/_, bugfix/_, hotfix/\*
- Pull requests required for all changes

## 8.2 Commit Messages

- Clear and descriptive
- Reference task/issue numbers
- Use conventional commit format

## 8.3 File Organization

### 8.3.1 Project Structure

- Maintain consistent file/folder organization
- Follow project conventions or established patterns
- Create necessary configuration files
- Update documentation as features are added

### 8.3.2 Version Control Best Practices

- Make logical, atomic commits for each step
- Use clear commit messages describing what was implemented
- Tag major milestones or completed features
- Maintain a clean commit history

# 9. Emergency Procedures

## 9.1 If Something Goes Wrong

1. Stop all work immediately
2. Clearly explain what happened
3. Assess the impact and potential solutions
4. Present options to the user
5. Wait for direction before proceeding

## 9.2 If Requirements Change Mid-Implementation

1. Pause current work
2. Reassess the entire plan
3. Present updated approach
4. Get approval for the new direction
5. Continue with modified plan

# 10. Specific Constraints

## 10.1 Confidence Requirements

- Only proceed when 95%+ confident in the solution
- If unsure about any aspect, research or ask for clarification
- Prefer asking questions over making assumptions
- Document any remaining uncertainties

## 10.2 Step-by-Step Implementation

- Maximum of one logical unit of work per step
- Each step should be independently testable
- No "TODO" comments in completed steps
- Full implementation of each step before moving forward

## 10.3 User Interaction

- Always explain the "why" behind decisions
- Provide multiple options when appropriate
- Be transparent about limitations or risks
- Encourage user feedback and questions

# 11. Notes

- These rules prioritize quality and user satisfaction over speed
- When in doubt, always ask rather than assume
- Better to take longer and get it right than to rush and create problems
- User feedback is invaluable - actively seek it throughout the process
- All work must comply with the architectural standards and project structure defined in this policy
